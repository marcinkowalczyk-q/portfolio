## Context

Business team needed independent management of promotional banners within offer listings. Previously, changes required developer support, slowing operations.

Banners operated in critical product areas and had to respect existing configurator architecture, Design System, and SEO/performance constraints.

## Challenge

Create an interface enabling non-technical users to control dynamic UI elements without violating system rules.

Solutions required balancing business speed, operational safety, existing architecture integration, and DS/SEO/performance compliance.

## Working within constraints

The interface had to integrate into the existing configurator hub, leverage the current Design System, and avoid additional developer burden. All solutions required SEO and listing performance review.

---

## Understanding the operational context

Analysis of banner management revealed the core issue wasn't visual design but lack of control and clear responsibility.

No central overview existed, system states were undefined, mistake-prevention mechanisms were absent, and all changes required developer involvement.

---

## From tasks to system logic

Operational issues were translated into a clearer system structure by defining behaviors across different situations.

Identifying clear states, valid transitions, and configuration rules reduced developer dependency and increased predictability for users.

![Flowchart of the campaign logic: empty-list check, adding a campaign through the form, required-field validation and publishing](/images/banner-configurator/system-logic.png)

## Designing within the Design System

The project used the existing Design System from inception, extending it with new variants for unsupported scenarios.

The solution became a natural system extension, maintaining consistency and predictable behavior for dynamic content management.

## Interaction flows as system definition

Flows defined system behavior rather than serving as visual screen maps, showing relationships between user actions, banner states, and product consequences.

Diagrams included conditions, constraints, and exceptions, helping developers understand what is allowed or blocked in specific contexts.

![Annotated flow from the banner list to the confirmation dialog: switching the publish toggle activates the campaign, arrows show the return to the list](/images/banner-configurator/interaction-flows.png)

## Error prevention & operational safety

The interface prioritized mistake reduction through additional confirmation for critical actions, blocking active element removal, and clearly distinguishing deactivation from deletion.

Form validation detected incorrect data before system-level changes — preventing rather than just handling errors.

![Confirmation dialog for unpublishing a banner, next to form validation errors for name length, URL format and background file format](/images/banner-configurator/error-prevention.png)

## System interface layers

The interface comprises connected layers supporting different stages of the management process rather than a single unified view.

### Banner List (system overview)

The list view acts as a control panel for the system. Users can see all banners, their states and usage context, which supports informed operational decisions. This view enables system control, not only content browsing.

![Banner list table with name, location URL, website and mobile app channels, and a publish toggle for each banner](/images/banner-configurator/banner-list.png)

### Configuration Form (rule definition)

The form is used to define how the banner should work. Users set parameters and content, but always within constraints defined by the system logic. The form is not a content creator, but an interface for defining rules.

![“Add banner” side panel over the list, with fields for name, location URL, channel, desktop and mobile background, alt text and banner copy](/images/banner-configurator/configuration-form.png)

### Preview (system feedback)

The preview acts as a feedback layer. It allows users to see how the configuration will affect the actual UI behavior in the product, reducing uncertainty and the risk of unwanted results.

![Preview panel showing the same Last Minute banner in the desktop/tablet and mobile layouts](/images/banner-configurator/preview.png)

## Scenarios (behavior outcomes)

Supporting content variants required considering multiple UI behavior scenarios, showing consequences of configuration decisions, not only visual variations.

Scenarios presented different active element sets and layout impacts, predicting system reactions before implementation while serving as a team communication tool.

![Content scenarios mapping configurator input to the rendered banner: heading only, heading and paragraph, with a button, and with two paragraphs and a button](/images/banner-configurator/scenarios.png)

## Usability testing

Scenarios from the analysis phase became the basis for testing. I built a prototype and tested it with two people: the main banner owner and the colleague who covers for them. For an internal tool, that is in practice the whole target group.

Testing led to three changes:

- **A data-href field** (the banner's target link). Its absence only surfaced while working through the scenarios.
- **A new form field order**, matching how users actually prepare banners.
- **Optional headings and copy**, so a graphic-only banner can be published.

I reviewed the final version with stakeholders and the development team, with whom I checked feasibility throughout. GA and Clarity data helped decide where the banner sits in the listing.

## Design documentation

Documentation covered scenarios, states, dependencies, and edge cases in Figma as the development source of truth.

It addressed system behavior and logic alongside layouts — essential for rules-based rather than visual-structure-only implementation.

![Figma documentation of the base banner list view: UX notes on columns, sorting and lazy loading next to the annotated screen](/images/banner-configurator/documentation.png)

## Implementation review

Once the test environment was ready, I reviewed the implementation on three levels:

- **Visual accuracy:** whether the build matches the design pixel for pixel.
- **Design system compliance:** whether the right components are used in the right variants, and whether styles come from tokens rather than hard-coded values.
- **Flow accuracy:** walking through every scenario to check it follows the agreed flow.

---

## Key takeaways

Operational tools require designing rules and constraints more than screens alone.

The greatest value came from translating business needs into system models — enabling independent user work while protecting product quality.

- UI acts as a control layer over system logic.
- Data validation and rules form the solution foundation.
- System constraints enable correct user action.
- Design System work increases consistency and predictability.
